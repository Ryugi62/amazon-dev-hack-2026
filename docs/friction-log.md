# Friction log - building an Alexa+ MCP add-on without Alexa+ access

Dates are 2026-10-16 (Korea Standard Time). "Tried" is what I ran; "Suggestion" is what would have saved me time. Each entry names the document or tool involved.

| # | Where | What happened (repro) | Cost | Suggestion |
|---|---|---|---|---|
| 1 | Alexa+ Developer Docs, page "Design Guide: Introduction" | The page header says "Fetch the complete documentation index at: /docs/llms.txt". `curl -L https://developer.amazon.com/docs/llms.txt` returns a 404 page. I also tried `/docs/alexaplus/llms.txt` and `/docs/alexaplus/add-ons/llms.txt`: both 404. | ~10 min; I had to scrape the sidebar instead | Publish the index at the advertised path, or correct the sentence. |
| 2 | Same docs, page links such as `.../mcp-addon-design-guide-overview.md` | The page's own link list includes `.md` variants. Requesting any of them (for example `.../mcp-toolkit-quickstart.md`) returns the site's "404 Page not found" page. The plain `.html` URL works. | ~10 min; the `.md` form is what a coding agent would try first | Serve the Markdown, or remove the `.md` links. |
| 3 | "Alexa+ Add-on Local Inspector" vs "Alexa+ MCP QuickStart Guide" | The quickstart says the server must support MCP spec 2025-11-25. The inspector page's example `initialize` request sends `"protocolVersion":"2025-06-18"`. A server that follows the quickstart strictly could reject the inspector's request. | Doubt about which version to negotiate; the negotiation behaviour is not documented either | Use one version in both pages and say how version negotiation should behave. |
| 4 | Local Inspector, "Installation" | The CLI `@alexa-ai/addon-local-inspector` is not on the public npm registry (`npm view @alexa-ai/addon-local-inspector` returns 404). The page says to log in to the Developer Console first. A hackathon entrant who has no Alexa+ access cannot run the one tool that checks widgets on the real device frames. | Could not use it; the card was checked only in my own stand-in host | Offer the inspector to hackathon entrants through a Devpost resource link, or publish it on npm. |
| 5 | "Design Guide: Layout and Rendering" | The page says the host passes `deviceClass` and calls it authoritative, but I found no list of its possible values on any page I read. The Local Inspector page names only two surfaces, "Small (10 inch and below)" and "Large (11 inch and above)". My stand-in host uses guessed names (`echo-show-8`, `echo-show-15`). | Guessing; the widget's size logic may not match the real values | List the allowed `deviceClass` values next to the `hostContext` field list. |
| 6 | Layout guide ("Block viewport ... Card viewport") vs Local Inspector ("Small / Large") | Two different ways to describe screen classes. The layout guide ties the viewport to orientation (taller than wide = Card). It does not say how that maps to Small and Large in the inspector report. | A design question I could not settle without a device | One table: surface name, size range, viewport type, example device. |
| 7 | `@modelcontextprotocol/ext-apps` 2.0.3 vs Alexa+ docs | The Alexa+ pages mention `_meta.ui.resourceUri`. The SDK package also contains the older flat key `ui/resourceUri`. The docs do not say whether Alexa+ reads both. | Wrote only the nested key and hoped | State which key(s) Alexa+ reads. |
